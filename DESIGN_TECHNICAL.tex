\chapter{System Purpose \& Scope}
% ============================================================================

The HFT Market Simulator is a distributed platform for evaluating algorithmic trading agents in a sandboxed, low-latency environment. It automates containerization (Python, Rust, Go, C++), enforces security isolation via Kubernetes, and provides real-time scoring based on throughput and latency metrics.

\textbf{Core Design Principle}: Decouple the high-performance matching engine (C++) from orchestration and telemetry layers (Python), using Kafka as a durable event log to prevent data loss.

\chapter{Architecture Overview}

\section{High-Level Components}

The system consists of seven integrated layers:

\begin{enumerate}
    \item \textbf{Frontend}: React + Vite (port 5173) — live leaderboard, charts
    \item \textbf{API Gateway}: FastAPI (port 8000) — submissions, SSE stream
    \item \textbf{Orchestrator}: Kubernetes, Docker — language detection, pod lifecycle
    \item \textbf{Data Stores}: Redis, Kafka, Zookeeper — events, scores, coordination
    \item \textbf{Contestant Pod}: K8s Pod (evaluation-sandbox namespace) — bot execution
    \item \textbf{Matching Engine}: C++ (port 8080) — order matching, latency tracking
    \item \textbf{Scoring Engine}: Python (subprocess) — validation, metrics, Redis updates
\end{enumerate}

\chapter{Key Design Decisions}
% ============================================================================

\section{C++ for Matching Engine}

\textbf{Why}: Latency-critical hot path demands compiled code, lock-free data structures, and CPU pinning.

\textbf{Implementation}: Single-threaded matching loop (Core 1), lock-free MPSC queue (65536 elements), std::map order book, histogram-based latency tracking (100k buckets × 1µs).

\textbf{Trade-off}: Low-level C++17 vs. development speed; no GC for predictable performance.

\section{WebSocket over Raw TCP}

\textbf{Why}: Standard protocol, firewall-friendly, Python library support, hand-rolled for latency control.

\textbf{Implementation}: Manual HTTP 101 upgrade, binary frame parsing (opcode 0x2), client masking (RFC 6455), 32-byte OrderMessage struct.

\textbf{Trade-off}: Custom WebSocket parsing adds complexity but enables precise latency control.

\section{Kafka for Trade Durability}

\textbf{Why}: Decouple matching from scoring; provide durable event log for replay.

\textbf{Implementation}: Single partition (total ordering), 60-byte packed TradeEvent, engine batches up to 1024 events per message, scoring engine reads with unique \texttt{group\_id} and \texttt{auto.offset.reset=latest}.

\textbf{Trade-off}: Kafka polling (50ms) adds latency, but prevents trade loss.

\section{Kubernetes for Sandbox}

\textbf{Why}: Standardized, declarative, multi-layer security (NetworkPolicy, Pod Security Standard, seccomp).

\textbf{Implementation}: \texttt{evaluation-sandbox} namespace with restricted PSS, NetworkPolicy egress to port 8080 only, \texttt{runAsNonRoot} (UID 10002), dropped ALL capabilities, read-only root FS.

\textbf{Trade-off}: K8s overhead vs. industry-standard security.

\section{Redis for Leaderboard}

\textbf{Why}: In-memory sorted sets ideal for ranking; Pub/Sub for SSE notifications.

\textbf{Implementation}: Sorted set (\texttt{ZADD leaderboard:scores}), hashes (\texttt{HSET contestant:meta}), Pub/Sub (\texttt{publish leaderboard\_updates}).

\textbf{Trade-off}: No persistence, but microsecond latency for updates.

\section{Matching Engine (C++)}

\textbf{Files}: \texttt{matching-engine/main.cpp}, \texttt{MatchingEngine.cpp}, \texttt{TCPServer.cpp}

\textbf{Threads}:
\begin{itemize}
    \item Core 0: Main thread (idle, graceful shutdown)
    \item Core 1: \texttt{processLoop()} — dequeue, match, record t2
    \item Core 2: \texttt{TCPServer::run()} — epoll, WebSocket parsing, record t1
    \item Core 3: \texttt{KafkaOffloader::run()} — drain SPSC queue, publish Kafka
\end{itemize}

\textbf{Data Structures}:
\begin{itemize}
    \item \texttt{OrderBook}: \texttt{std::map<price, vector<Order>>} (buy/sell sides)
    \item \texttt{MPSCQueue<Order>}: 65536-element lock-free ring
    \item \texttt{SPSCQueue<TradeEvent>}: 65536-element lock-free ring
    \item Histograms: 100k buckets (latency tracking per thread)
\end{itemize}

\textbf{Matching Algorithm}:
\begin{lstlisting}[language=cpp]
while (bestBid >= bestAsk) {
    tradedQty = min(buyQty, sellQty);
    executionPrice = makerPrice;
    t2 = system_clock::now();
    publish_to_kafka(TradeEvent{...});
    erase_matched_orders();
}
\end{lstlisting}

\section{Orchestrator (Python)}

\textbf{File}: \texttt{infra/orchestrator.py}

\textbf{Responsibilities}:
\begin{enumerate}
    \item Load K8s config (\texttt{\~/.kube/config})
    \item Create \texttt{evaluation-sandbox} namespace
    \item Apply NetworkPolicy (egress :8080)
    \item Auto-detect language (Python/Rust/Go/C++)
    \item Generate Dockerfile
    \item Build image via Docker
    \item Spawn scoring engine subprocess
    \item Apply pod, wait for completion
    \item Cleanup (delete pod, kill scoring)
\end{enumerate}

\textbf{Language Detection}: \texttt{requirements.txt}/\texttt{sandbox\_sdk.py}/\texttt{.py} → Python; \texttt{Cargo.toml}/\texttt{.rs} → Rust; \texttt{go.mod}/\texttt{.go} → Go; default → C++.

\section{Scoring Engine (Python)}

\textbf{File}: \texttt{telemetry/scoring\_engine.py}

\textbf{Flow}:
\begin{enumerate}
    \item Create Kafka consumer (unique \texttt{group\_id})
    \item Poll with 50ms timeout
    \item For each TradeEvent:
    \begin{itemize}
        \item Unpack 60-byte struct
        \item Validate (monotonic ID, timestamp order, no self-match)
        \item Record engine latency (t2 - t1)
    \end{itemize}
    \item Every 1 second:
    \begin{itemize}
        \item Compute TPS, P50/P90/P99 (10-second window)
        \item Score = TPS / max(p99\_us, 0.1)
        \item Update Redis (ZADD, HSET, PUBLISH)
    \end{itemize}
\end{enumerate}

\textbf{Validation Checks}:
\begin{itemize}
    \item \texttt{match\_id == last\_match\_id + 1} (no gaps)
    \item \texttt{t0 < t1 < t2} (timestamp order)
    \item \texttt{buy\_order\_id != sell\_order\_id} (no self-match)
    \item \texttt{price > 0 and finite} (valid price)
    \item \texttt{qty > 0} (valid quantity)
\end{itemize}

\textbf{Disqualification}: First validation failure → score = -1.0 (permanent, ranks last).

\section{API Gateway (FastAPI)}

\textbf{File}: \texttt{telemetry/api.py}

\textbf{Endpoints}:
\begin{itemize}
    \item \texttt{POST /api/v1/submissions/upload}: Extract ZIP, spawn orchestrator
    \item \texttt{GET /api/v1/leaderboard}: Return top 25 (ZREVRANGE)
    \item \texttt{GET /api/v1/leaderboard/stream}: SSE (Redis Pub/Sub)
\end{itemize}

\textbf{Design}: Async event loop, background tasks, non-blocking pub/sub.

\section{Frontend (React + Vite)}

\textbf{File}: \texttt{leaderboard/src/App.jsx}

\textbf{Features}:
\begin{itemize}
    \item EventSource (SSE) for live updates
    \item Table: rank, contestant, score, TPS, P50/P90/P99, correctness, fills
    \item Bar chart (top 10 scores)
    \item Line chart (top 10 P99 latencies)
    \item Theme toggle
\end{itemize}

\chapter{Scoring Formula}
% ============================================================================

\begin{equation}
\text{score} = \frac{\text{TPS}}{\max(\text{p99\_latency\_us}, 0.1)}
\end{equation}

\textbf{Rationale}:
\begin{itemize}
    \item \textbf{Numerator}: Rewards high throughput, incentivizes participation
    \item \textbf{Denominator}: Penalizes tail latency, reflects SLA requirements
    \item \textbf{Ratio}: Creates trade-off between speed and latency
\end{itemize}

\begin{table}[H]\small
    \centering
    \begin{tabular}{cccc}
    \toprule
    \textbf{TPS} & \textbf{P99 ($\mu$s)} & \textbf{Score} & \textbf{Interpretation} \\
    \midrule
    1000 & 100 & 10.0 & Balanced \\
    1000 & 10 & 100.0 & Exceptional \\
    100 & 1 & 100.0 & Ultra-low latency \\
    100 & 100 & 1.0 & Poor \\
    10 & 10000 & 0.1 & Critical \\
    \bottomrule
    \end{tabular}
\end{table}

\textbf{Disqualification}: Any correctness violation → score = -1.0 (always last).

\chapter{Security Model}
% ============================================================================

\section{Isolation Layers}

\textbf{Layer 1: Container Isolation}
\begin{itemize}
    \item \texttt{runAsNonRoot: true} (UID 10002)
    \item \texttt{readOnlyRootFilesystem: true} (no persistence, no escape)
    \item \texttt{allowPrivilegeEscalation: false} (no setuid)
\end{itemize}

\textbf{Layer 2: Capability Dropping}
\begin{itemize}
    \item All Linux capabilities dropped (CAP\_NET\_RAW, CAP\_SYS\_ADMIN, etc.)
    \item seccomp: RuntimeDefault (curated syscall whitelist)
\end{itemize}

\textbf{Layer 3: Network Isolation}
\begin{itemize}
    \item NetworkPolicy: egress restricted to \texttt{10.0.2.2:8080}
    \item Cannot reach other pods, internet, internal services
\end{itemize}

\textbf{Layer 4: Filesystem Isolation}
\begin{itemize}
    \item Read-only root FS (no write, no escape vector)
    \item No access to host filesystem
\end{itemize}

\chapter{Assumptions \& Constraints}
% ============================================================================

\section{Assumptions}

\begin{enumerate}
    \item \textbf{Synchronized Clocks}: t0, t1, t2 on different machines require NTP sync
    \item \textbf{Kafka Availability}: Trade loss acceptable only if permanently down
    \item \textbf{Single Evaluation}: 60-second window, scores reset between submissions
    \item \textbf{Honest Submissions}: No intentional protocol violations
    \item \textbf{Stateless Matching}: No order cancellation or modification
\end{enumerate}

\section{Constraints}

\begin{table}[H]\small
    \centering
    \begin{tabular}{ll}
    \toprule
    \textbf{Constraint} & \textbf{Reason} \\
    \midrule
    Throughput: ~10k TPS & Single core bottleneck \\
    Concurrent bots: ~170 & TCP limit per process \\
    P50 Latency: ~5-10µs & Cache hits, empty queue \\
    Order book size: 100k levels & DRAM bounded \\
    Kafka retention: 7 days & Disk space constraint \\
    \bottomrule
    \end{tabular}
\end{table}

\chapter{Implementation Details}
% ============================================================================

\section{Protocol Wire Format}

\textbf{OrderMessage} (Bot $\rightarrow$ Engine) — 32 bytes, little-endian:
\begin{lstlisting}
[0-7]    order_id (uint64)
[8-15]   t0_ns (uint64, nanoseconds)
[16-23]  price (double, IEEE 754)
[24-27]  qty (uint32)
[28]     side (uint8: 1=BUY, 2=SELL)
[29-31]  padding (zeros)
\end{lstlisting}

\textbf{TradeEvent} (Engine $\rightarrow$ Kafka) — 60 bytes, packed:
\begin{lstlisting}
[0-7]    match_id (uint64, monotonic)
[8-15]   buy_order_id (uint64)
[16-23]  sell_order_id (uint64)
[24-31]  t0_ns (uint64, taker's bot time)
[32-39]  t1_ns (uint64, gateway ingest)
[40-47]  t2_ns (uint64, match time)
[48-55]  price (double)
[56-59]  qty (uint32)
\end{lstlisting}

\section{CPU Pinning Strategy}

\begin{itemize}
    \item \textbf{Core 0}: Reserved for OS, interrupts, jitter
    \item \textbf{Core 1}: \texttt{MatchingEngine::processLoop()} (hot path)
    \item \textbf{Core 2}: \texttt{TCPServer::run()} (network I/O)
    \item \textbf{Core 3}: \texttt{KafkaOffloader::run()} (Kafka publishing)
\end{itemize}

Pinning isolates latency-sensitive threads from OS scheduler preemption.

\section{Concurrency Model}

\textbf{Matching Engine}:
\begin{itemize}
    \item Lock-free MPSC queue (TCPServer $\rightarrow$ MatchingEngine)
    \item Lock-free SPSC queue (MatchingEngine $\rightarrow$ KafkaOffloader)
    \item Histograms flushed every 65536 orders (batched locking)
\end{itemize}

\textbf{Scoring Engine}:
\begin{itemize}
    \item Single-threaded (Kafka consumer loop)
    \item Sliding 10-second window
    \item Redis operations atomic
\end{itemize}

\textbf{API Gateway}:
\begin{itemize}
    \item Async event loop (uvicorn + asyncio)
    \item Concurrent SSE clients (non-blocking pub/sub)
\end{itemize}

\chapter{Conclusion}
% ============================================================================

The HFT Market Simulator achieves low-latency evaluation through:

\begin{enumerate}
    \item \textbf{Native C++ matching engine} with lock-free queues and CPU pinning
    \item \textbf{Kafka durability} preventing trade loss
    \item \textbf{Kubernetes sandboxing} with multi-layer security
    \item \textbf{Async Python orchestration} for non-blocking management
    \item \textbf{Real-time feedback} via Redis Pub/Sub and SSE
\end{enumerate}

The system is production-ready for local development and scales to cloud deployments via Terraform. Key trade-offs prioritize latency and correctness over throughput ceilings and persistent storage.
